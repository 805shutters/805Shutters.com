# Scheduling release verification

## October 25 output ownership and full speech regression

The owner clarified that v29 literally said "silent" after Thursday. The prepared
time question was stored, but the old media adapter bound the first response ID
without establishing that it belonged to the supplied question. An automatic VAD
response could take that position. The repair buffers each response and releases
audio only when its completed transcript matches the exact prepared line. Missing,
cancelled, unrelated or mismatched output cannot arm a confirmation. The existing
bounded recovery remains active. Diagnostic records contain IDs, byte counts and
match flags, never caller speech or audio.

Real-provider testing exposed a second defect: xAI emitted a `completed` input
caption such as "1 2" before VAD ended, then emitted the complete address under
the same item ID after `speech_stopped`. Replying to the prefix reconfigured the
session mid-sentence and caused the complete answer to be lost. The repair keeps
audio flowing until VAD ends, accepts the final caption, and suppresses duplicates.
Leading spoken house-number digits are normalized and still read back for approval.

The opt-in `services/voice-805/test/provider-harness.mjs` uses the actual media
adapter and real xAI TTS, 8kHz G.711 input, VAD, transcription and speech output.
The generated outgoing bytes are independently transcribed to check spoken content.
Only fixed fictional callers are used; audio stays in memory. Carrier playback
acknowledgements and calendar availability/save responses are simulated. No Twilio
call, real CRM appointment or external message is generated by the harness.

Separately, `conversation.database.test.ts` runs the complete media conversation
through real scheduling functions, availability snapshots, PostgreSQL state CAS,
atomic booking RPC and calendar read-back in PGlite. Only the external geocoder
and speech transport are replaced. It proves no early-yes save, one durable
attributed appointment after confirmation, duplicate suppression, and no partial
booking when a published slot is withdrawn before the final yes. This is not a
production booking or a real handset test.

The real-provider matrix passed 13 complete conversations with 119 independently
transcribed output clips across nine scenarios: booking, no-fit callback, date/time
and address correction, flexible day, alternative time, declined confirmation,
duration question, past-date correction and unclear-input callback. Both caller
voices and 0/250/600ms state delays were exercised. The final two runs used the
full production readback, including the callback number. Expected lines, actual
audio transcripts, response IDs and hashes are in
`provider-verification-20261025.json`; it contains synthetic identities only.

The first gate-only provider runs failed on the premature address prefix. Those
failures drove the VAD-end repair; they are not counted among the passing runs.
Automated gates passed: 197 voice tests; 833 website test files with 10,609 tests
(six files/36 tests skipped); typecheck; and production build. Two full
conversation/database tests separately verified atomic saves and withdrawn-slot
rejection. These results do not replace the owner's final handset acceptance.

## Earlier verification layers

The Oct 25 handset failures exposed gaps in the event simulation. Successful
transcript parsing did not prove that the next spoken question reached the caller.
The original fixture generally delivered a final caption followed by an uninterrupted
scripted response. It missed audio-history captions preceding final captions,
duplicate final captions clearing the next question, and VAD speech-start signals
discarding a question without a completed replacement answer.

The 18:12 Pacific call on Edge v28 persisted an appointment request, October 30,
and 10:00, then produced no played address-question checkpoint. Caller input
was accepted; the output lifecycle failed. No appointment was saved. The exact
audio content and every intermediate event are unavailable because calls are not
recorded. Reproduced event failures support the repairs; they do not prove every
event that occurred on that handset call.
